End-to-end proof

One primitive. Four pages. Three modes.

Every frame below renders through the same RecordTable — one render function, one block of CSS. The pages differ only in a config object, and each config is printed under its frame. If those configs are small and declarative, the pattern generalises; if any page needs a special case, that shows up here rather than on page seven of a migration.

The four are chosen to break it, not to flatter it: packages is the easy read-only case, admin/users puts live controls inside an expanded row, secrets has a real editor that expansion cannot hold, and usage has no record at all — it is only a table, which is the mode that replaces four hand-rolled ones.

The account shell is untouched everywhere: 200 px rail, 72 rem cap, both breakpoints. Drag to 390 px to see the same markup become cards.

It generalises — with three things I got wrong first

			

				Four pages, four configs of 13–15 lines each, no per-page CSS. But
				building it surfaced three things the survey alone did not:
			

			
    
				
  1. 
					mode has to be a prop, not two components.
					I had planned RecordTable and a separate list-over-detail
					layout. Secrets proves they are the same component: identical toolbar,
					table, columns and metadata band, differing only in where the record
					renders. Two components would have duplicated all of that.
				
    2. 
				
  2. 
					Columns need per-column drop priority, not a breakpoint.
					My first pass dropped columns at one width for every page. Usage has
					five columns that all matter and packages has two that do not, so the
					priority belongs in the column config — drop: 1|2|3 — and
					the card fallback at 620 px catches whatever is left.
				
    3. 
				
  3. 
					Expand mode must not cap the list's height. I gave
					every mode the same scrolling list. In expand mode the record renders
					inside that scroller, so the record ends up trapped in a
					nested scroll you have to fight to read — visible the moment
					admin/users unfolded eight fields and a role cluster. Pane and none
					modes keep the cap, because there the cap is what keeps the record
					below reachable. Only found this by building it.
				
    4. 
			

			

				Where it does not fit:
				account/stars and the community listings are content, not
				records — a title, a description, a star count. Those want the card grid
				they already have. I would leave them alone and let the
				MetadataGrid fix reach them instead.
			

			

				Ready to build for real. Two commits as before: the
				content layer (MetadataGrid auto-fit, IdValue,
				13 call sites) then RecordTable with packages as its first
				consumer. The API this proof settled on:
			

			
RecordTable({
  mode: 'expand' | 'pane' | 'none',
  columns: [{ key, label, align?, drop?, render? }],
  rows, selectedId, buildHref,       // rows stay real links
  toolbar: [ …controls ],
  renderRecord?: (row) => nodes,
  countLabel,
})
