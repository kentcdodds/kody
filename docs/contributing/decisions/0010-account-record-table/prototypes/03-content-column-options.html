Where I'd go: 1, and the content fixes underneath all of them

Stacking wins because it needs no judgement call per page. Every one of the 14 list/detail pages can adopt it, editors and all, and it's the only one that also fixes the phone — where a 434 px pane was never the issue but three 115 px metadata columns were. Option 2 is a nice upgrade for read-only, uniform pages later; option 3 only if you tell me seeing both at once beats both being readable.

  1. The content fixes first, on their own. MetadataGrid goes auto-fit / minmax(14rem, 1fr) and loses its columns prop at 13 call sites; ids become single-line copy chips; timestamps get nowrap; the search index moves behind a disclosure with a scroll box. This lands value even if we never touch the layout.
  2. Then the stack, on Packages alone. A narrowOrder-style prop on AccountManagementLayout won't cover it — this wants a sibling ListOverDetail layout with the toolbar row and the table. Live with it on one page before migrating the other thirteen.

Frames are built from the app's own tokens and both shipped typefaces, with the shell, rail, gutters, 72rem cap and the 860/1100 px breakpoints transcribed from account-management-components.tsx.
