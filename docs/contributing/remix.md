# Remix guidance

Use the repo-local Remix skill instead of vendoring generated Remix package
documentation in this repository.

The repo-local skill lives at:

- `.agents/skills/remix/SKILL.md`

Load that skill before changing Remix routes, controllers, middleware, data
access, validation, auth, sessions, file uploads, server setup, UI components,
hydration, navigation, frames, or tests.

For `<Frame>` partial reloads, see [frames](./frames.md).

`npx remix@next new <app>` copies this skill from the Remix CLI bootstrap
template. The CLI does not expose a standalone `remix skills install` command.

## Kody runtime topology

Kody deploys as a Cloudflare Worker, not as the Node HTTP server generated by
`remix new`. The production request path is:

`packages/worker/src/index.ts` -> `packages/worker/src/app/handler.ts` ->
`packages/worker/src/app/router.ts`

Keep these Worker-specific differences when comparing Kody with the default
template:

- Wrangler supplies canonical Fetch API `Request` objects. Kody does not use
  `remix/node-fetch-server`, so its Node-only `trustProxy` option does not
  apply.
- `npm run deploy` builds and deploys the Worker; there is no long-running
  `npm start` process.
- Development uses the esbuild watcher plus `wrangler dev`. Production client
  assets use the same esbuild pipeline with minification enabled.
- Static files are served through the Workers Assets binding rather than
  `remix/assets` or `remix/static-middleware`.
- Frame resolution is configured in both `packages/worker/client/entry.tsx` and
  `packages/worker/src/app/ssr-render.tsx`.

If a Node server entry point is added later, evaluate `trustProxy` only at that
trusted reverse-proxy boundary. Do not copy it into Worker request handling.
