How Kody works

  1. Ask once
  2. Save the answer shape
  3. Ask again from any agent
  4. Get notified
LIVE: switch to https://kody.codes/guides/how-kody-works. This is the interactive transcript, not a blog post. Walk the factory loop. Ask once: search finds githubAccessToken + a memory, execute fetches public events, then save as a package. Ask again: later, on a phone with a different host, the same question invokes the package. Get notified: package-owned daily cron, email_send only when the list is not empty. Punchline: a question you would ask again becomes an export you can invoke from any agent, then a daily email that stays quiet until something actually shipped.

Everyone's building agents.

Kody is your agent's platform for your personal software.

Thesis of the talk. Everyone's building agents. Kody is the platform those agents use to build your personal software — not a chatbot, not a hardcoded tool list. Steal the ideas even if you never use the product.

Four questions the platform has to answer

  1. Where does memory live?
  2. How does the agent discover what it can do?
  3. How do secrets stay out of the chat?
  4. How does a one-off script become software?
These four are the map for the rest of the hour. We'll walk them in order: discovery (search/execute), durability (packages), secrets/auth, then long-lived work and git.

Two tools. That's the whole public API.

searchexecute

Learning outcome 1. Cloudflare Code Mode: don't dump 400 tools into the host context window. search: discover capabilities, packages, integrations, secrets (metadata only). execute: run a short ESM module that calls what search found. The agent doesn't hardcode gmail.searchMessages. It finds the capability, then writes the call.

Discover, then invoke

  1. A registry, not a hardcoded tool list
  2. Each capability ships its exact call shape
  3. The agent writes the glue
Walk the loop: question → search → pick a hit → get the TypeScript input/output → execute. Contrast with MCP servers that expose every tool as a top-level function. Packages show up in the same search path as builtins. Concrete example: this morning, "find the Joe Eames webinar in my email" → google package → Gmail on the business account.

execute is a scratchpad

  • One-offs, smoke tests, experiments
  • Thrown away on purpose
Use execute when the code is disposable: inspect an API, try a composition, run something once. Ambient user authority — great for exploration, dangerous as a permanent home. Signal to stop: you rewrote the same module twice, you want a schedule, you need tests, multiple files, or declared secrets.

When it's worth keeping, it becomes a package

  • A real repo, rooted at package.json
  • Exports, jobs, apps, workflows, subscriptions
  • Versioned, reviewable, schedulable
Learning outcome 2. A package is not a saved prompt. It's software: source, tests, README Intent, declared secrets and hosts. Scheduling alone is not a reason to package — ad hoc jobs exist. Package-owned jobs when the schedule belongs to reusable behavior.

The package lifecycle

  1. Invoke what already exists
  2. execute for a one-off
  3. Prefer a close community package
  4. Then create or evolve a durable package
Spine of the talk. Slow down. Search first. Don't rewrite Gmail. Community listings are excluded from general search — that's why community_search exists. Prefer trusted. Fork, review, adapt, publish. Create only when nothing suitable exists. Escalate from execute when they'll run it again, it needs a durable surface, or you're calling a third-party product API for real.

Auth is not the product API

  • Integrations hold the tokens
  • Packages teach the agent how to call the product
Learning outcome 3. Google OAuth is credentials. @kentcdodds/google is the maintained Gmail/Calendar/Drive helper — including which account to use. This webinar's thread lived in business Gmail. Personal Gmail didn't have it. Account-aware packages matter. Host allowlists are load-bearing: a real bearer token is attached, so requests can only go to approved hosts.

Secrets never belong in the transcript

  • Stored server-side
  • Referenced in code. Never pasted into chat.
Gmail scopes, refresh tokens, API keys — none of that should land in the host's context or logs. Packages declare the secrets they need. Users approve. Runtime injects {{secret:name}}. Prefill the save URL so setup is a click. Same idea for OAuth connect links.

Some work has to stay alive

  • Jobs and workflows outlive the chat
  • Subscriptions, inbound email, webhooks
Request/response is not enough. Jobs for schedules and retries. Workflows when the work has to be durable and cancellable. Subscriptions: package-declared handlers for events like email received. Inbound email and webhooks arrive on their own — the package reacts. Email is the easy example. Implementation detail (jobs vs runtime worker) only if someone asks how it runs on Cloudflare.

Coding agents get a git lane

  • clone -> edit -> test -> push -> publish
  • The repo is the source of truth
This is how you keep agents from becoming irreproducible prompt soup. Git lane for coding agents. Tool-only lane (repo sessions) when there's no filesystem. Test scheduled wrappers before enabling them. dryRun is a package contract, not platform magic. Confirm live mutations with the user. Don't patch generated runtime state instead of changing source.

The same loop, live

  • search until you find the capability
  • execute a one-off
  • keep it only if it's worth a package

Three things to leave with

  1. A registry: search, then execute
  2. A lifecycle: one-off, then community, then a package
  3. Ops: secrets, auth vs helpers, durability, git
